# Paul AI Trader v3 — Canonical Data Model

**Status:** Working specification  
**Safety default:** `LIVE_TRADING=false`  
**Primary production database:** PostgreSQL  
**Development/test compatibility:** SQLite only where behavior is equivalent

---

## 1. Purpose

This document defines the authoritative data model for Paul AI Trader v3. The model is designed to make paper trading deterministic, auditable, broker-neutral, and safe to migrate incrementally from the existing v2 implementation.

The model separates:

- market reference data,
- time-series market observations,
- strategy analysis,
- risk approval,
- orders and fills,
- accounting ledger entries,
- derived positions,
- runtime execution history,
- user-visible performance snapshots,
- security and audit records.

No browser state, in-memory cache, or broker response is an accounting source of truth.

---

## 2. Global conventions

### 2.1 Identifiers

Use UUIDs generated by the application for all domain records that may cross service or database boundaries.

Recommended forms:

- UUIDv7 where supported for time-ordered identifiers.
- UUIDv4 as an acceptable fallback.
- Broker/external IDs remain separate fields and are never primary keys.

### 2.2 Time

- Store timestamps in UTC.
- Use timezone-aware datetime values.
- Record both event time and ingestion time where they differ.
- Never overwrite the original event timestamp with processing time.

### 2.3 Money and quantities

- Use fixed-precision decimal database types.
- Never use binary floating-point values for money, quantity, fees, cost basis, or P&L.
- Every monetary value must identify its currency.
- Every market quantity must respect venue precision and minimums.

Recommended defaults, subject to venue-specific validation:

```text
money_amount:      NUMERIC(28, 10)
asset_quantity:    NUMERIC(36, 18)
price:             NUMERIC(28, 10)
percentage/rate:   NUMERIC(18, 10)
```

### 2.4 Immutability

The following records are append-only after creation except for operational metadata explicitly listed:

- fills,
- ledger entries,
- strategy analyses,
- risk decisions,
- runtime events,
- audit events,
- market candles after finalization.

Corrections use compensating records, not destructive mutation.

### 2.5 Soft deletion

Trading and accounting records are never soft-deleted. Reference/configuration records may use `is_active` and validity ranges.

### 10.3 Ledger invariants

1. Each ledger transaction has at least two entries.
2. Entries balance under the defined accounting convention.
3. The same fill cannot post twice.
4. Fees post separately from gross trade value.
5. Corrections use compensating transactions.
6. Cash and asset changes are committed atomically with the fill.
7. Derived balances equal the sum of immutable entries.

## 15. Database transaction boundaries

The following operations must be atomic:

1. Paper fill creation + ledger transaction + ledger entries + lot update + order state transition.
2. Order rejection + order event + audit event.
3. Strategy analysis + signal decision.
4. Risk decision + reservation of capital when an order will be submitted.
5. Cancellation + release of reserved capital.
6. Compensating correction transaction + audit event.

External broker calls cannot be enclosed in a database transaction. Use a durable intent/state machine and reconciliation by idempotency key.

---

## 16. Retention and archival

Initial policy until usage evidence exists:

- Orders, fills, ledger entries, audits: retain indefinitely.
- Strategy/risk decisions: retain indefinitely for explainability.
- Runtime events: retain at least 180 days; aggregate older events.
- Quotes: retain according to storage budget; candles are preferred for long history.
- Candles used in backtests: retain or version by provider/source checksum.
- Performance snapshots: retain indefinitely.

A retention job must never delete records required to reproduce accounting or a reported backtest.

---

## 17. Migration rules from v2

1. Inventory existing tables, models, and Alembic heads before schema changes.
2. Map current paper orders to canonical orders without inventing unknown fill details.
3. Preserve original IDs in dedicated legacy-reference columns or mapping tables.
4. Introduce ledger records through a controlled opening-balance migration.
5. Reconcile opening equity before enabling v3 write paths.
6. Run dual-read or shadow-calculation comparison before switching dashboard queries.
7. Never migrate paper records into future live accounts.
8. Every migration has forward, validation, and rollback instructions.

---

## 18. Required data-model tests

- Decimal precision and rounding at venue boundaries.
- Duplicate client order ID rejection.
- Duplicate fill idempotency.
- Balanced ledger transaction enforcement.
- Insufficient available cash rejection.
- Reservation and release of capital.
- Partial fill accounting.
- Full and partial position close under the selected lot policy.
- Fee allocation and realized P&L.
- Rebuild positions from ledger/fills.
- Market-data freshness and quality handling.
- Immutable strategy/risk versions.
- Runtime-cycle idempotency.
- PostgreSQL migration from a clean database.
- SQLite compatibility tests only for supported development paths.

---

## 19. Definition of done

The canonical data model is ready for implementation when:

- the current v2 audit identifies every existing persistence source,
- accounting identities are approved,
- fee and lot policies are explicit,
- PostgreSQL types and constraints are finalized,
- migration sequencing is documented,
- repository interfaces are specified,
- all critical transaction boundaries have integration tests,
- no live-order capability is enabled.
